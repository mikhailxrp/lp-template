# CLAUDE.md — контекст проекта для AI-агента

Этот файл читается агентом автоматически. Правила здесь имеют приоритет над
общими привычками агента, но подчиняются `.claude/rules/general.md`.

---

## 1. Контекст проекта

**Что делаем:** статическую вёрстку сайта (Stage 1), которая затем вручную
сажается на WordPress в виде кастомной темы (Stage 2).

**Ключевое следствие:** вёрстка пишется не «чтобы просто выглядело», а так,
чтобы её можно было механически разрезать на PHP-шаблоны без переписывания.
Любое решение, которое усложнит посадку, — неверное, даже если визуально работает.

**Stage 1 (текущий этап):**

- только HTML / CSS / JS
- **ни одного PHP-файла** в проекте
- никаких сборщиков, npm, node_modules, package.json
- контент — реальный или максимально близкий к реальному (не lorem ipsum)

**Stage 2 (не сейчас, но верстаем с оглядкой):**

- кастомная тема WP 6.x, PHP 8.1+
- кастомные поля — Redux Framework + metaboxes (не ACF)
- правила этапа: `.claude/rules/wordpress.md`

## 2. Стек

| Слой       | Что используем                                              |
| ---------- | ----------------------------------------------------------- |
| Сетка      | Bootstrap 5 — только `container / row / col-*`              |
| Раскладка  | Flexbox (основной инструмент), CSS Grid — точечно           |

**Правила структуры:**

- вендорные файлы **не редактируем** никогда; переопределяем в `style.css`
- шрифты — локально в `assets/fonts/` (папку создать при первом шрифте),
  подключение через `@font-face` в `style.css`, `font-display: swap`

## 4. Порядок подключения ассетов

**В `<head>`:**

```html
<link rel="stylesheet" href="assets/css/vendor/bootstrap.min.css" />
<link rel="stylesheet" href="assets/css/vendor/owl.carousel.min.css" />
<link rel="stylesheet" href="assets/css/style.css" />
```

**Перед `</body>`:**

```html
<script src="assets/js/vendor/jquery-3.7.1.min.js"></script>
<script src="assets/js/vendor/bootstrap.bundle.min.js"></script>
<script src="assets/js/vendor/owl.carousel.min.js"></script>
<script src="assets/js/main.js"></script>
```

Порядок фиксированный: jQuery всегда первым, `main.js` всегда последним.
`style.css` всегда после вендорных стилей.

> **Версия jQuery.** На Stage 1 ставим jQuery 3.x (по умолчанию 3.7.1), версия из
> макета донора не важна. Плагины донора должны работать на 3.x (проверка на
> шаге «Библиотеки», START.md 2б). При посадке сверяем версию ядра:
> `jQuery.fn.jquery`. Версию записываем в `.docs/direction.md`.
>
> **Для Stage 2:** все эти подключения уходят в `wp_enqueue_style()` /
> `wp_enqueue_script()` с зависимостями и `filemtime()`. Локальный jQuery при
> посадке **удаляется**, используется jQuery из ядра WP.

## 5. HTML: правила разметки

### 5.1 Семантика

- каркас страницы: `<header> <main> <footer>`, внутри — `<section>`, `<article>`, `<nav>`, `<aside>`
- `<div>` — только для сетки и группировки без смысла
- один `<h1>` на страницу, иерархия заголовков без пропусков (h1 → h2 → h3)
- заголовок уровня **не выбирается ради размера шрифта** — размер задаётся классом

### 5.2 Секции и WP-маркеры

Каждая секция страницы оформляется одинаково — это и есть будущий `template-part`:

```html
<!-- @wp: template-parts/sections/hero.php -->
<section class="lp-hero" id="hero" aria-labelledby="hero-title">
	<div class="container">
		<div class="row align-items-center">
			<div class="col-lg-6">
				<h1 class="lp-hero__title" id="hero-title">Заголовок</h1>
			</div>
		</div>
	</div>
</section>
<!-- /@wp: hero -->
```

Требования:

- у каждой секции — свой BEM-блок `.lp-<section>` и стабильный `id`
- `id` осмысленный и латиницей — он же якорь для навигации и цитирования
- секции не вложены друг в друга и не делят общий контейнер

### 5.2а Вне секций: каркас, шапка, подвал, модалки

Порядок в `<body>` фиксированный:

```html
<body>
	<a class="lp-skip-link" href="#main">...</a>

	<!-- @wp: template-parts/header/navigation.php -->
	<!-- /@wp: navigation -->

	<main id="main">...секции в своих маркерах...</main>

	<!-- @wp: template-parts/footer/footer.php -->
	<!-- /@wp: footer -->

	<!-- @wp: template-parts/modals/callback.php -->
	<!-- /@wp: callback -->

	<script type="application/ld+json">
		...
	</script>
	<script src="..." defer></script>
</body>
```

Правила:

- **Каждая модалка** — отдельный маркер `template-parts/modals/<имя>.php`, после подвала и до `<script>`. Внутри секции модалку не держим: Bootstrap ломает её позиционирование, если у родителя есть `overflow` или `transform`.
- Всё вне маркеров `/wp-slice` не режет: `doctype`, `<head>`, skip-link, `<main>`, `<script>`, JSON-LD. Это каркас, его на Stage 2 пишем руками.
- Всё остальное, что живёт вне секций (cookie-баннер, кнопка «наверх», прелоадер), оформляем так же: свой маркер и свой файл.

Куда это попадает в теме:

| Из статики                               | В теме                                                                                             |
| ---------------------------------------- | -------------------------------------------------------------------------------------------------- |
| `doctype`, `<head>`, `<body>`, skip-link | `header.php` вручную (`wp_head()`, `wp_body_open()`)                                               |
| Шапка                                    | `template-parts/header/navigation.php`, меню через `wp_nav_menu()`                                 |
| `<main>` и секции                        | `front-page.php` или шаблон страницы, секции через `get_template_part()`                           |
| Подвал и модалки                         | `template-parts/footer/`, `template-parts/modals/`, вызываются из `footer.php` перед `wp_footer()` |
| `<script>`                               | `wp_enqueue_script()`                                                                              |
| JSON-LD                                  | SEO-плагин (см. 10.3)                                                                              |

### 5.3 Повторяющиеся элементы

Всё, что на Stage 2 станет репитером Redux, помечаем:

```html
<!-- @wp-repeat: services -->
<div class="lp-services__item">...</div>
<div class="lp-services__item">...</div>
<!-- /@wp-repeat -->
```

Внутри повторяющегося блока разметка у всех элементов **идентична**:
никаких «у третьей карточки чуть другая структура». Различия — только через
модификатор-класс.

### 5.4 Что нельзя в HTML

- инлайн-стили (`style="..."`) — ни одного
- инлайн-обработчики (`onclick`, `onchange`)
- пустые `<div>` ради отступов
- текст в `<img>`-ах вместо текста (кроме логотипа)
- вложенные `<a>` и интерактив внутри интерактива

## 6. Сетка и раскладка

**Алгоритм выбора:**

```
Нужны колонки с отступами и брейкпоинтами?  → Bootstrap row / col-*
Нужно выровнять / распределить элементы?    → Flexbox
Двумерная раскладка, которую flex делает
криво (масонри, сложная сетка карточек)?    → CSS Grid в .lp-* классе
```

Конкретика:

- Bootstrap-сетка — **только** `container`, `container-fluid`, `row`, `col-*`, `g-*`
- утилиты Bootstrap CSS Grid (`.grid`, `.g-col-*`) — **запрещены**
- flex-утилиты Bootstrap (`d-flex`, `justify-content-*`, `align-items-*`, `gap-*`) — можно
- собственный CSS Grid — можно, но в своём `.lp-*` классе и с обоснованием в комментарии
- вёрстка mobile-first: базовые стили без медиазапроса = мобильный, дальше `min-width`
- брейкпоинты — только бутстраповские: 576 / 768 / 992 / 1200 / 1400

**Утилиты vs собственные классы:** если на элементе набирается больше 4–5 утилит
Bootstrap — выносим в `.lp-*` класс. Смесь `col-lg-4 d-flex flex-column gap-3
text-center mb-4 p-3 border rounded` — признак, что нужен свой класс.

## 7. CSS

### 7.1 Токены

Источник истины — `direction.md`. В начале `style.css` он превращается в блок
`:root` с CSS custom properties (пример формата, актуальные имена и значения
смотри в `style.css`):

```css
:root {
	--lp-color-primary: #e9a23b;
	--lp-color-text: #1a1a1a;
	--lp-space-md: 1rem;
	--lp-radius-card: 12px;
	--lp-font-heading: 'Название шрифта', sans-serif;
}
```

**Хардкод цветов, шрифтов, отступов, радиусов в правилах запрещён.** Всегда
`var(--lp-*)`. Если нужного токена нет — не выдумываем значение, а спрашиваем.

Переопределение переменных Bootstrap (`--bs-primary` и т.п.) — допустимо, и это
предпочтительнее, чем перебивать его правила через специфичность.

### 7.2 Типографика: роли шрифтов

Шрифты берём из макета и записываем в `direction.md` (раздел «Шрифты»). В коде их
два, по ролям. Названия и начертания живут только в токенах `:root`.

| `--lp-font-heading` (структура и акцент) | `--lp-font-body` (объёмный текст) |
| ---------------------------------------- | --------------------------------- |
| `h1`, `h2`, `h3`                         | подзаголовки и лиды               |
| текст кнопок и CTA                       | абзацы, описания                  |
| числа в ценах                            | текст внутри карточек             |
| числа и текст в бейджах                  | вопросы и ответы FAQ              |
| подписи карточек                         | пункты списков                    |
|                                          | подписи форм, сноски, футер       |

**Логика разделения:** акцентный шрифт работает на коротких строках и задаёт
структуру, текстовый нужен там, где его читают долго.

**Правила:**

- в CSS всегда `font-family: var(--lp-font-heading)` / `var(--lp-font-body)`,
  никогда название шрифта строкой
- шрифтов в коде два, по ролям; если в макете больше двух — не добавляй сам,
  спроси; если в макете один — оба токена получают одно значение, роли остаются
- акцентный шрифт на абзаце длиннее 2–3 строк и текстовый на `h1`–`h3` — ошибка,
  если макет не делает так явно; тогда отступление записываем в `direction.md`
- `h4`–`h6`, если появятся: по умолчанию текстовый шрифт с усиленным весом
- шрифты самохостятся в `assets/fonts/`, подключаются через `@font-face`
  с `font-display: swap`; начертания — только реально используемые
- в `<head>` preload-ится только начертание заголовочного шрифта, попадающее
  в первый экран

### 7.3 Именование

- BEM с префиксом: `.lp-block__element--modifier`
- один блок = одна секция или один переиспользуемый компонент
- утилитарные собственные классы — с префиксом `.lp-u-` и только если реально переиспользуются

### 7.4 Порядок свойств в правиле

```
позиционирование → box model → типографика → визуал → анимация
```

### 7.5 Ограничения

- `!important` — только для утилит-оверрайдов, с комментарием почему
- вложенность селекторов не глубже 2 уровней
- никаких `#id` в качестве селектора стилей
- никаких магических чисел: `margin-top: 37px` → токен или расчёт с комментарием

## 8. JavaScript

### 8.1 Структура `main.js`

Один файл, модульная организация, инициализация в одном месте:

```js
(function () {
	'use strict';

	// В WP jQuery работает в режиме noConflict: глобального $ нет
	const $ = window.jQuery;

	const initHeader = () => {
		/* ... */
	};

	const initHeroSlider = () => {
		if (!$) return;
		const $slider = $('[data-js="hero-slider"]');
		if (!$slider.length) return;

		$slider.owlCarousel({
			items: 1,
			loop: true,
			nav: false,
			dots: true,
			responsive: {
				768: { items: 2 },
				992: { items: 3 },
			},
		});
	};

	document.addEventListener('DOMContentLoaded', () => {
		initHeader();
		initHeroSlider();
	});
})();
```

### 8.2 Правила

- JS-хуки — только через `data-js="..."`, **не через классы стилей**
  (классы меняет верстальщик, `data-js` — контракт со скриптом)
- каждая init-функция начинается с проверки наличия элемента и `return`,
  если его нет — страниц много, скрипт один
- параметры Owl всегда прописываем явно (`items`, `loop`, `nav`, `dots`,
  `responsive`) — не полагаемся на дефолты
- никаких глобальных переменных вне IIFE
- jQuery берём только через `const $ = window.jQuery`; глобальный `$` не используем
  (в WP его нет); init-функции, которым нужен jQuery, начинаются с `if (!$) return;`
- ошибки обрабатываем явно: нет данных / нет элемента → тихий выход, а не падение
- анимации/эффекты — CSS, если только они не требуют логики

> **Для Stage 2:** данные, которые придут из PHP (URL AJAX, nonce, тексты),
> на Stage 1 берём из `data-*` атрибутов на элементе. Не из захардкоженных
> констант внутри `main.js` — иначе на посадке придётся переписывать логику.

## 9. Изображения и медиа

- формат: WebP основной, JPG/PNG — фолбэк через `<picture>` там, где критично
- **всегда** `width` и `height` атрибутами (защита от CLS)
- `loading="lazy"` на всё ниже первого экрана; на изображения первого экрана —
  `loading="eager"` + `fetchpriority="high"`
- `alt` — осмысленное описание, а не «картинка» и не список ключевиков;
  у декоративных `alt=""`
- имена файлов латиницей, через дефис, осмысленно: `uslugi-montazh-krovli.webp`
- иконки — инлайн SVG или один SVG-спрайт; **не иконочный шрифт**

## 10. SEO — встраиваем в вёрстку

SEO не «добавляется потом». На Stage 1 закладывается вся техническая база.

### 10.1 Шаблон `<head>`

```html
<!doctype html>
<html lang="ru">
	<head>
		<meta charset="UTF-8" />
		<meta name="viewport" content="width=device-width, initial-scale=1" />

		<title>Заголовок страницы — до 60 символов</title>
		<meta
			name="description"
			content="Описание 140–160 символов, с пользой и конкретикой"
		/>
		<link rel="canonical" href="https://example.ru/page/" />

		<meta property="og:type" content="website" />
		<meta property="og:title" content="..." />
		<meta property="og:description" content="..." />
		<meta
			property="og:image"
			content="https://example.ru/assets/img/og-image.jpg"
		/>
		<meta property="og:url" content="https://example.ru/page/" />
		<meta property="og:locale" content="ru_RU" />
		<meta name="twitter:card" content="summary_large_image" />

		<link rel="icon" href="/favicon.ico" sizes="any" />
		<link rel="apple-touch-icon" href="/apple-touch-icon.png" />

		<!-- на dev-стенде обязательно, снять перед продом -->
		<meta name="robots" content="noindex, nofollow" />
	</head>
</html>
```

> **Для Stage 2:** title / description / canonical / OG ведёт SEO-плагин (поля в
> админке), тема их не выводит (см. `wordpress.md`, 7b). На Stage 1 прописываем
> статикой как источник текстов и **не вкладываем их в template-part**. В тему
> они не копируются: в `header.php` остаются только `title-tag` и `wp_head()`.

### 10.2 Обязательное в разметке

- `lang="ru"` на `<html>`
- один `<h1>`, иерархия без пропусков
- хлебные крошки на всех внутренних страницах + `BreadcrumbList` JSON-LD
- внутренние ссылки с осмысленным анкором (не «здесь», не «подробнее» в одиночку)
- внешние ссылки: `rel="noopener"`, при необходимости `nofollow`
- `<nav>` с `aria-label` для каждой навигации на странице
- контент не подгружается JS-ом — весь значимый текст в исходном HTML

### 10.3 JSON-LD

Кладём в конце `<body>`, отдельным `<script type="application/ld+json">` на
каждый тип. Минимальный набор для сайта услуг:

- `Organization` (или `LocalBusiness` — см. GEO) — на всех страницах
- `WebSite` — на главной
- `BreadcrumbList` — на внутренних
- `FAQPage` — если на странице есть блок вопрос-ответ
- `Service` / `Product` — на страницах услуг/товаров
- `Person` — на блоке эксперта/автора

> **Для Stage 2:** `Organization`, `WebSite`, `BreadcrumbList` выводит SEO-плагин,
> статические версии из Stage 1 в тему не переносятся. `FAQPage`, `Person`,
> `LocalBusiness` добавляем своим кодом только если плагин их не даёт
> (см. `wordpress.md`, 7b).

```html
<script type="application/ld+json">
	{
		"@context": "https://schema.org",
		"@type": "Organization",
		"name": "Название",
		"url": "https://example.ru/",
		"logo": "https://example.ru/assets/img/logo.png",
		"telephone": "+7 999 000-00-00",
		"address": {
			"@type": "PostalAddress",
			"streetAddress": "...",
			"addressLocality": "...",
			"addressRegion": "...",
			"postalCode": "...",
			"addressCountry": "RU"
		}
	}
</script>
```

Правило: **JSON-LD описывает только то, что реально есть на странице.** Разметка
FAQ без видимого FAQ-блока — нарушение и риск санкций.

### 10.4 Производительность (часть SEO)

- критичные шрифты — `<link rel="preload" as="font" crossorigin>`
- не более 2 начертаний на шрифт без необходимости
- изображения первого экрана — оптимизированы и не тяжелее необходимого
- никаких блокирующих скриптов в `<head>`

## 11. GEO

Термин используем в двух смыслах — оба закладываются в вёрстку.

### 11.1 GEO как Generative Engine Optimization (видимость в AI-выдаче)

Цель: чтобы LLM (Алиса, ChatGPT, Perplexity, AI Overviews) могли **извлечь и
процитировать** контент со страницы.

| Правило                          | Как реализуем в разметке                                                               |
| -------------------------------- | -------------------------------------------------------------------------------------- |
| Answer-first                     | первый абзац секции — прямой ответ на вопрос из заголовка, 1–2 предложения             |
| Самодостаточные блоки            | абзац понятен вне контекста: без «как сказано выше», «этот способ»                     |
| Конкретика                       | цифры, сроки, цены, условия в тексте, а не на картинке                                 |
| Вопрос-ответ                     | блок FAQ с `<h3>`-вопросами + `FAQPage` JSON-LD                                        |
| Таблицы                          | реальный `<table>` с `<caption>` и `<th scope="col">`, не div-сетка                    |
| Определения                      | `<dl>` / `<dt>` / `<dd>` для терминов и характеристик                                  |
| Списки                           | `<ul>` / `<ol>` вместо абзацев с тире                                                  |
| Экспертность (E-E-A-T)           | блок об авторе/эксперте с `Person` JSON-LD, регалии текстом                            |
| Доступность контента для парсера | текст всегда в DOM; аккордеон **скрывает визуально**, а не подгружает контент по клику |
| Цитируемость                     | стабильные `id` у секций — прямые якоря `#faq-dostavka`                                |

Дополнительно в корне проекта — `llms.txt` (простой Markdown: что за сайт, ключевые
страницы, факты о компании, контакты). Файл статический, переносится на Stage 2 как есть.

**Антипаттерны GEO:**

- ключевой ответ спрятан в слайдере или табе, который рендерится JS-ом
- цифры и условия только на изображении-инфографике
- «водные» вводные абзацы перед сутью
- разные формулировки одного факта в разных местах сайта

### 11.2 GEO как гео-локальная оптимизация (привязка к региону)

Если у проекта есть географическая привязка (город, регион, зона выезда):

- `LocalBusiness` JSON-LD вместо `Organization`, с `address`, `geo`
  (`latitude` / `longitude`), `areaServed`, `openingHoursSpecification`
- **NAP-консистентность**: название, адрес, телефон — в одном и том же
  формате на всех страницах и в JSON-LD, символ в символ
- адрес в подвале в микроразметке `<address>` + семантические теги
- телефон ссылкой `<a href="tel:+79990000000">`, e-mail — `mailto:`
- город/регион упомянут в `<title>`, `<h1>`, тексте первого экрана — естественно,
  без переспама
- карта — `<iframe loading="lazy">` ниже первого экрана; **не грузим её скриптом
  при загрузке страницы**

> Если проект не имеет географической привязки — блок 11.2 пропускаем целиком,
> `LocalBusiness` не ставим.

## 12. Доступность (a11y)

- контраст текста не ниже 4.5:1 (крупный — 3:1)
- фокус видим: не убираем `outline` без замены на свой видимый стиль
- вся интерактивность доступна с клавиатуры; порядок табуляции логичен
- кнопка без текста → `aria-label`
- модалки, аккордеоны, табы — на компонентах Bootstrap (у них ARIA из коробки),
  свои реализации только при явной необходимости
- у слайдера — работающая клавиатурная навигация и `aria-label` у стрелок
- формы: каждый `input` связан с `<label for>`; ошибки — текстом, не только цветом

## 15. Как работать с этим файлом

- задача непонятна → задай **один** уточняющий вопрос до написания кода
- нужного токена нет в `direction.md` и `:root` → спроси, не выдумывай значение
- правило конфликтует с задачей → скажи об этом явно и предложи альтернативу
- перед использованием API библиотеки → проверь актуальную документацию (Context7)
- правишь существующий код → меняй только то, о чём просили
